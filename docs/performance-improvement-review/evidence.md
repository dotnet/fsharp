This is the source-to-rule contract, not an implemented agent. [corpus.md](corpus.md) fixes discovery to **2026-04-22 through 2026-09-22**, with evidence cutoff `2026-09-22T09:28:34Z`. [validation.md](validation.md) freezes RED cases before implementation. G1-G8 below are the eight future output rows, not eight unconditional benchmark demands.

**Attribution:** `human-derived` means verified feedback with the role and limits below; `request-required` means a binding requirement of this sprint, not invented maintainer consensus. Both labels may apply. The request explicitly identifies the human exchange on #20348 and the author withdrawal on #20352; complete packets and historical code corroborate those narrow interpretations. Other user-account prose remains unverified unless independently established. In particular #20261's model-associated review, #20416's explicitly AI-generated review/inline comments, uncertain comments, bots, existing agents and synthetic cases contribute **zero human-derived votes**. Their claims may be inspected as input, not promoted into human rules.

Two PRs in two distinct families supply the human-derived observations here: `FAMILY-inline-copy` and `FAMILY-self-profile`. Each observation has **one** supporting PR/family, not recurring consensus; replies, approvals and alternate revisions do not add votes. Author withdrawal is not reviewer rejection. A request to measure is not a demonstrated defect. Empty approval endorses no imagined rule; merged/closed state determines no outcome.

Contrary context remains in the corpus, not discarded for a stronger-sounding rule: #20287's [reader-closure concern](https://github.com/dotnet/fsharp/pull/20287#discussion_r3811931627) was [withdrawn after examining shared ownership](https://github.com/dotnet/fsharp/pull/20287#discussion_r3811998107); #20285's [cold FSharp.Core allocation trade-off](https://github.com/dotnet/fsharp/pull/20285#discussion_r3829823873) was accepted in context. The large IL-retention family does not turn related changes into independent consensus.

## Conditional metric mapping

Choose the primary measurement from the actual claim and investigate only implicated trade-offs. Do not require all rows for every PR.

| Claim/workload | Primary measurement | Related trade-off to test when relevant | Human source IDs or request origin |
| --- | --- | --- | --- |

## Tooling context, not human evidence

At checkout `ae294143e5890033fcb717956050a91a6f2ed6e8`, [benchmark guidance](../../tests/benchmarks/README.md) distinguishes compiler/service work from generated-program runtime and cautions about environment differences. [Historical FCS comparison](../../tests/benchmarks/FCSBenchmarks/BenchmarkComparison/README.md) measures `FSharpChecker.ParseAndCheckFileInProject`; its per-version BenchmarkDotNet processes and API compatibility defines need recording. A `ParseAndCheckProject` retention claim is not automatically covered by that single-file benchmark.

[Compiled-program benchmarks](../../tests/benchmarks/CompiledCodeBenchmarks/README.md) use `tests\benchmarks\CompiledCodeBenchmarks\MicroPerf\MicroPerf.fsproj`. `Program.fs` configures `Current` as baseline and `Preview` as a custom build configuration; the project selects preview language/local compiler for that configuration. These labels are **not baseline/PR commit identities**. Verify the binaries, runtime, flags and compiler versions actually used on both sides.

When appropriate, [BuildWithLocalFSharp.fsx](../../eng/scripts/BuildWithLocalFSharp.fsx) supplies local compiler/core overrides after a Release packed build; its `--verify` mode checks the resolved FSharp.Core version in assets files, not the compiler binary's identity. Retain the actual compiler path/version separately. This is tooling choice, not a mandatory matrix or a benchmark result. The existing `expert-reviewer` remains responsible for broad compiler review; these rules request behavior proof only where a performance mechanism could change it.
